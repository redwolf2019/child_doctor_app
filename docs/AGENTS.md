# 设计文档写作约定

本文件约束 `docs/` 下的架构设计、产品设计、流程设计、使用说明、通信协议、API 设计和架构决策记录。目标很简单：让同事看得懂、能评审，也能照着实施。

写 `docs/` 下任何文档前先读本文。用户对当前任务的明确要求覆盖本文的默认写法；系统级指令和安全限制始终有效。

## 1. 先确认事实，再动笔

- 项目已有约定和仓库中的事实比通用经验可靠，以它们为准。
- 先查代码、配置、接口定义和已有文档。仓库里能确认的内容，不留给读者猜。
- 不编造需求、指标、性能数据、临床结论或外部依赖。暂时无法确认的信息放进「待确认项」，写明它会影响什么。
- 缺失的信息会改变方案方向，而且无法从仓库确认时，再问用户。其他情况可以注明假设后继续写。
- 同一术语全文只用一个名字。首次出现时解释，后面不要为了避免重复而换同义词。

## 2. 默认交付方式

默认输出 Markdown。用户指定其他格式就照办。

开头用一两句话说清文档要解决的问题，以及已经确定的目标或结论。正文先讲全局判断，再展开依据和细节。章节只为内容服务；没有内容的章节直接删掉，不照模板凑数。

表格适合字段定义、状态映射和方案对比。列表适合并列事项。完整的因果和取舍用段落讲清楚，不要把所有内容都切成碎片。

## 3. 文风

写给一起做事的同事，不写成宣传稿，也不保留聊天机器人的客套话。

| 避免 | 改法 |
| --- | --- |
| 「随着业务发展」「为了更好地」一类开场 | 直接写问题、结论或约束 |
| 「综上所述」「希望本文档有所帮助」一类收尾 | 写到最后一条有效信息就停 |
| 「高性能」「灵活」「显著提升」等空泛评价 | 给出指标、边界或可观察结果 |
| 赋能、抓手、闭环、一站式、全方位等营销词 | 换成做、支持、合并、减少等具体动词 |
| 「一般来说」「业界认为」等模糊归因 | 给出来源；没有来源就写成待验证假设 |
| 每节固定三点、每项都是「粗体词：解释」 | 有几项写几项，句式不必整齐 |
| 「让我们来看」「你会发现」等对话腔 | 直接陈述内容 |
| 用同义词反复改称同一对象 | 固定术语，允许自然重复 |
| 「各有优劣，按实际情况选择」 | 明确选什么、为什么选，以及代价 |

句子要有长有短。长句说明因果，短句下判断。能删且不损失信息的句子就删；能套在任何项目上的段落，通常也该删。

技术判断要落到事实上：写「超时 3 秒，最多重试 2 次，退避 200ms/400ms」，不要写「完善的重试机制」。选型需要说明放弃了什么、在哪些条件下会失效或需要重选。临时方案、已知缺陷和待验证假设照实记录。

## 4. 图和表怎么选

关系用文字讲不清时再画图。出现下列情况，正文应配 Mermaid：

- 流程包含多个角色、判定分支或异常回路；
- 三个及以上参与方之间存在调用顺序；
- 对象有明确的生命周期和状态迁移；
- 数据表之间存在需要评审的主外键关系；
- 多个模块的依赖或数据流仅靠列表难以核对。

单步操作、两项直接映射或一小段文字已经能说清的关系，不必画图。图要补充正文，不能只是把同一句话换成方框。

| 内容 | Mermaid 图类型 |
| --- | --- |
| 业务流程、操作流程、判定分支 | `flowchart` |
| 接口调用、报文交互 | `sequenceDiagram` |
| 状态迁移 | `stateDiagram-v2` |
| 数据模型、表关系 | `erDiagram` |
| 模块、类、组件结构 | `classDiagram` |
| 里程碑和排期 | `gantt` |
| 占比分布 | `pie` |

节点名称要短，正文负责解释。复杂系统拆成几张有明确主题的小图。交付前检查 Mermaid 语法，并逐项核对图中的名称、方向和分支是否与正文一致。有渲染工具就实际渲染；没有则做静态语法检查，并注明尚未完成渲染验证。

## 5. 不同文档该写什么

下面是内容边界，不是固定目录。与当前主题无关的条目不要硬塞进文档。

### 架构设计

说明背景、目标和系统边界，给出整体架构、核心组件职责、关键数据流与部署方式。技术选型要写依据和代价。性能、可用性、扩展性和安全只写能量化或能验证的要求，同时记录风险及应对办法。

### 产品设计

明确用户、使用场景、问题、目标和非目标。功能按优先级排列，区分 MVP 与后续版本；复杂交互补充用户流程、页面或对象状态。指标必须写清计算口径、数据来源和观察周期。

### 流程设计

写清参与角色、输入输出、主流程和异常分支。每个判定节点都要有去向。涉及外部调用时，补充 SLA、超时、重试、补偿或回滚策略。

### 使用说明

先说明适用对象和前置条件，再给最短可行的上手路径。操作步骤使用编号，每一步都写预期结果。配置项、常见问题和故障排查按读者实际会遇到的顺序组织；必要时附术语表。

### 通信协议设计

说明协议用途、适用范围和分层。帧或报文字段需标明名称、类型、长度、字节序、编码、取值范围、必填性和默认值。交互时序、状态机、握手、鉴权、心跳、重传、超时、错误码与版本兼容策略按实际协议取舍，不能遗漏已经存在的异常路径。

### API 设计

先确定接口风格、鉴权方式，以及统一请求和响应约定。每个端点写明方法、路径、输入、输出和错误；字段表包含类型、必填性、约束、默认值与说明，并提供可运行或可校验的请求/响应示例。分页、过滤、排序、限流、幂等和版本策略只在适用时展开。

### 架构决策记录

一条 ADR 只记录一个已拍板的决定。写清背景、选择、放弃的方案、代价，以及什么变化会触发重新评估。不要把 ADR 写成设计说明书。已经拍板且会约束后续实现的技术决定，写入 `docs/adr/`，不要只留在聊天记录里。

## 6. 记录不确定性和取舍

事实、假设和待确认项要分开。待确认项至少写清问题和影响；如果已有负责人或截止时间，也一并记录。

方案对比不能只列优缺点。先给选择，再说明判断依据、付出的代价，以及什么变化会触发重新评估。没有数据支撑时就写「尚未验证」，不要用看似精确的数字填空。

## 7. 交付流程

1. 完成初稿，核对需求覆盖、事实来源、术语和前后口径。
2. 做第二轮技术检查，核对字段、类型、单位、示例、边界条件、异常分支以及图文一致性。
3. 输出给用户前，必须运行 humanizer-zh 技能做最后一轮文字编辑，删除模板化排比、空话、营销词、过度加粗和其他 AI 写作痕迹。改写不能改变技术含义、数字、术语或约束。技能来源见 [Humanizer-zh](https://github.com/op7418/Humanizer-zh)。
4. 按 Humanizer-zh 的五项标准评分；总分低于 45/50 时继续修改并重新检查。
5. Humanizer-zh 处理后只做事实、链接、格式和语法校验。如果这一步发现正文还要改，改完后再运行一次该技能。技能不可用或未执行时，不得把文档标记为已完成。

两轮检查和 Humanizer-zh 处理都必须真实执行，不能只在文末声称「已检查」。

## 8. 交付前清单

- [ ] 开头已经说清问题和目标或结论
- [ ] 内容来自已确认事实，假设与待确认项已单独标明
- [ ] 术语、名称、数字、类型和单位前后一致
- [ ] 技术选型包含理由、代价和重新评估条件
- [ ] 分支、异常、超时、回滚或补偿没有悬空路径
- [ ] 图表确有必要，Mermaid 语法正确且与正文一致
- [ ] 字段约束、默认值、错误和示例足以支持评审或实现
- [ ] 已删掉空话、营销词、聊天腔、装饰性符号和无意义加粗
- [ ] 已完成两轮检查，并在最后一次正文修改后运行 Humanizer-zh
- [ ] Humanizer-zh 评分不低于 45/50
